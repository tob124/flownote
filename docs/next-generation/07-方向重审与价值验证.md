# FlowNote 下一代方向重审：从功能清单到个人认知支持

R3 调研稿，2026-09-23。本文件修订 R2 的产品判断，不要求本轮写代码。Get 笔记继续是采集、知识调用和成果流程的参照，但不再是产品上限或完整需求来源。产品价值方向先于视觉；用户现已允许启动独立 UI/UX 调研，见11。

## 1. 对现有计划的结论

R2 对数据安全、来源、成本、旧版兼容的约束有价值，05/06也足以描述一个可施工的功能集合。缺口在价值论证：它默认“采集→分类→问答→洞察→成果”自然会形成第二大脑。实际上，用户可能得到的是更多资料、更多 AI 卡片和更多页面，仍不知道过去哪条经验现在值得用、哪些判断已经过期、下一步该做什么。多一个模板或按钮不能证明认知负担下降。

| R2 假设 | 重新判断 | 对施工计划的影响 |
|---|---|---|
| Get 功能映射可定义完整 3.0 | 只能定义能力下限和竞品用语；FlowNote 的上限由个人长期价值决定 | 01的映射保留为参考，05的功能不再自动等于发布必做 |
| 有来源问答足以构成“记忆” | 引用能定位材料，仍可能遗漏相反证据、误解时间变化 | 须评估跨时段更新、冲突、拒答和证据缺失 |
| 主题知识库是长期思考的容器 | 容器可以很空或很乱；核心是围绕持续议题形成判断并回看变化 | 先验证主题是否让用户更快找回关键资料、完成一个真实问题 |
| 关联/反思/点评可按固定数量生成 | 数量不是价值；无关联或无新意时应不生成 | 用“被采纳的具体洞见”衡量，允许空结果 |
| Dream 报告＋成果工作台带来下一步 | 报告可能好看但无法行动；成果可能只是普通 AI 写作 | 验证能否找出被遗忘的承诺、未解决的问题、变化的观点，并帮助跟进 |
| 网页可提取就算解读 | 导航栏混入、动态页缺文、作者观点被误写为事实都会破坏信任 | 分别验收抓取、理解、与我的资料建立联系，见08 |
| “推荐书”加一个模型提示词即可 | 未核对书目会虚构，宽泛推荐也缺个人价值 | 必须先验证书目目录、个人需求及理由；未通过不进产品，见08 |

上述是对当前计划的分析判断，不是对 Get 或任何产品实际效果的实测结论。当前未在用户真实知识库或竞品账号中做体验测试。

## 2. 新的产品目标和边界

产品目标：**在一个具体问题出现时，FlowNote 能可靠地找回我已经知道的东西，显示它如何随时间改变，帮助我形成自己的判断，并让重要意图有机会被回看与推进。** 它应是个人记忆和思考的助手。“life leader”作为体验愿景，可以表现为提醒盲点和提供有依据的下一步选项；软件不替用户决定人生目标、消费或重大选择。

要形成明显升级，应同时具备四种能力：

1. **记得准确。** 原话、时间、来源、我自己的判断与外部作者的观点分开；更正之后旧版本不能继续被当作现状。
2. **在场景里想得深。** 不止汇总相似材料，还能找反例、解释变化、指出缺口；证据不够时敢说不知道。
3. **把想法带回来。** 根据当前议题、用户明确的目标或复盘时机，少量呈现过去的重要材料及“为什么现在相关”，可关闭或忽略。
4. **让思考产生后续。** 一个洞见可转为用户确认的结论、待验证问题、决定或下一步；以后能回看当时依据与后来结果。

这形成两个需要分别验证的闭环：**记忆闭环**（采集→校正/标注→准确召回→反馈纠错）和**推进闭环**（议题/目标→证据与选择→用户决定→回看结果）。旧的自动分类→Wiki→Dream 继续运行，但必须在这些闭环里证明有用，不能因保留历史功能就自动成为首页中心。

维持用户已确认的硬边界：Windows/Electron 优先；坚果云仍做同步/中转；JSON/Markdown 数据可读；DeepSeek/PaddleOCR 和低成本；个人自用；不新增语音、账号后台或自有云；移动端只可选轻量采集。本轮只写文档。

## 3. 外部研究给出的提醒

- [LongMemEval](https://arxiv.org/abs/2410.10813)把长期记忆拆成信息提取、跨会话推理、时间推理、知识更新和应当拒答五类。我们的“答对事实题”测试不够；个人笔记变更和前后矛盾尤其要单列。论文是通用基准，不能直接证明 FlowNote 用户收益。
- [RAGChecker](https://arxiv.org/abs/2408.08067)强调把检索错误和生成错误分开诊断。来源编号合法只能排除一类伪引文，无法证明召回完整或结论合理。FlowNote 应保存候选证据、选入证据和拒答原因供评估。
- [Readwise Reader](https://docs.readwise.io/reader/guides/ghostreader/overview)同时提供选中文段、整篇和资料库层级的提问。这提示“在阅读现场产生问题”可能比新增独立聊天页更有价值；这是设计推断，需用场景验证。其[解析说明](https://docs.readwise.io/reader/docs/faqs/parsing)也明确公开网页无法百分百正确提取。
- [Readwise 回顾](https://docs.readwise.io/readwise/docs/faqs/reviewing-highlights)展示了可调节的旧材料重现频率，也提供相关推荐。可借鉴“可控、可忽略、可调节”的机制，不照搬每日打卡或向用户强推通知。

研究还不足以决定唯一架构。本轮明确不做语义检索、向量库或 embedding；也不能由长期记忆论文推导知识图谱/自治代理。关键词检索的局限作为可见限制，先在本地真实规模和成本边界内比较轻量方案。

## 4. 优先验证的真实任务

| 任务 | 用户成功的样子 | 最低对照组 | 会失败的情况 |
|---|---|---|---|
| 过去我对 X 怎么看？现在有何改变？ | 找到两个时期的原话、变化点和未确定处，可直接打开来源 | 当前全文搜索＋手工读笔记 | 把旧看法写成当前立场；相反材料漏检 |
| 这篇新网页和我已有的想法有什么关系？ | 提取可靠；区分作者主张与我的笔记；指出新增、重复、冲突；给出处 | 存 URL＋手动摘要 | 页面未读全却声称全读；把推广内容当核心观点 |
| 我围绕目标 Y 还有什么悬而未决？ | 只基于用户明确记录的目标和决定，指出未完成承诺、阻碍或该复查的假设 | 主题列表＋手动搜索 | 从几条零散记录推断人生目标；频繁打扰 |
| 我接下来值得读哪本书？ | 对一个具体问题给少量可核验书目，说明与现有阅读的关系及未知之处 | 手动书目搜索 | 虚构书/版本、重复已读、把简介当读过全文 |
| 一月后回看一个决定 | 找得到当时选项、依据、反对意见、决定和后来结果 | Markdown 日志 | 只生成漂亮复盘，没有下一次可用的经验 |

用户已选择“持续推进目标与复盘”为最高优先级，因此优先验证表中目标 Y 与“一月后回看一个决定”，再用“过去看法变化”和网页对照增强证据质量。书籍推荐排在目标闭环之后，仍先做书目与效用研究，不因 R2 的页面安排直接实现。成果工作台先验证一件真实成果是否明显比用户直接写 Markdown 更省力。详细目标旅程见09。

## 5. 最小信息模型：哪些是事实，哪些只是推断

R2 的 Note/SourceRef/Collection 仍可用。若要支持长期判断，需在下一轮规格中增加最小的**用户确认层**：用户自己明确的议题、目标、决定或待验证问题。最初可以只是带类型和引用的简短记录，不预设复杂知识图谱。

任一系统生成的“记忆/建议”必须带：原始出处与版本、涉及时间、生成时间、确定/推断/待确认状态、用户采纳或纠正记录。作者观点、模型总结、用户原话、用户确认的结论不能混为一谈。旧来源失效时降级显示；同一主题出现冲突时并列说明，不擅自合并成“你的稳定偏好”。自动关联结果只作候选，不写成已确认事实。用户纠错后，相关缓存失效，并使后续建议不再重复同一错误。

“主动”只从用户显式设立的议题/目标、用户打开应用或手动复盘开始；不从全库笔记暗推人格画像，不后台持续调用模型。第一次可做“本周值得回看”的**手动入口**，最多展示少量、有解释的候选；能关闭、忽略、标记无关。是否升级为定时提醒要等可用性数据，而不是先建通知体系。

## 6. 重新排序与决策门槛

R2 的 T00–T03、来源保留、错误恢复、成本上限、引用校验是必要地基，可保留。T04–T22 目前是**候选施工蓝图**，不是“按序把所有功能做出来就会达到 next level”的证明。用户已确认的综合升级方向仍有效；我们先把“怎么做才有用”验证清楚，再锁定 Sol 的任务顺序和验收值。

每个弹性功能在施工前提供一页决策卡，至少回答：用户何时遇到该问题；输入从何而来；输出如何回到真实动作；最低对照体验；主要错误类型；无数据/无网络/证据不足如何表现；会发送哪些隐私内容；每次可能花费；如何通过小样本验证；若未通过应降级到什么能力。缺一项，不进入正式版强制范围。

| 门槛 | 需要的证据 | 不通过时 |
|---|---|---|
| G0 真实问题 | 用户已选“持续推进目标与复盘”；再写出一个最近发生的过程与现有替代做法即可启动该主线 | 不以功能名立项 |
| G1 可核对材料 | 用合成/公开夹具先覆盖时间变化、冲突、错误网页、中文书籍；记录输入和期待结果 | 保留原始资料与手动入口 |
| G2 早期效用比较 | 先用纸面/可点击原型或受限假数据演示，与当前 FlowNote（或搜索＋手写）对比完成同一问题；此阶段允许制作可丢弃原型，不要求完整系统 | 缩小流程或放弃附加 AI |
| G3 成本与信任 | 用假 API 和少量授权样本估算调用次数、错误解释与拒答；正式体验数值留待试用 | 调整触发/缓存/范围，不能只提高调用预算 |
| G4 进入 Sol 正式施工 | 交付具体示例、反例、数据契约、失败态、验收夹具，再更新05/06；G2可先做受限原型 | 维持 R2 候选，不让 Sol 猜产品意图 |
| G5 限量试用与发布 | 正式实现后，用用户自选真实任务跨数周检验持续价值、误判、打扰与实际成本 | 未达标则缩小/回退，不宣称长期第二大脑 |

阈值不能凭空宣称已达到。建议 G1–G3 先用约20个公开/合成场景排除明显错误；G4 后的 G5 才由用户自选约10个真实、可匿名记录结果的任务与现有流程对照。不要求研究文档读取真实库或记载私人原文。评估记录任务结果、耗时、成本和错误类别；跨数周回看是发布/价值检验，不是制作原型的前置条件。20/10是发现问题的起点，不是统计显著性承诺。

## 7. 对旧文档的立即修订规则

- 01保留 Get 能力地图，但不得以其功能覆盖率判断 FlowNote 的最终体验。
- 02中的网页提取、索引和问答是**可靠的底层候选**；“提取成功”与“解读有帮助”分开验收。
- 05中的主题、洞察、Dream、成果细节是 R2 工作假设。页面数、固定3条洞察、固定模板及旧的产品验收阈值都可被验证结果修改。
- 06的施工任务编号可用来管理依赖，暂不当作无条件开工令。以后给 Sol 的任务包必须附 G4 决策卡。
- 08专门讨论网页解读与书籍推荐。UI/视觉另见11的独立调研，不以 Get 的视觉作为模板。

## 8. 当前需要的下一步调研产物

1. 先为目标设立→受阻/行动→复盘→调整决定制作公开/合成场景集，附正确出处与失败态；网页和书籍再按08验证来源可用性，目标细节见09。
2. 在不接入真实个人数据的前提下，画出问题出现→系统候选→用户判断→结果回看的完整交互文字流程。
3. 用对照试验决定保留、缩小或删除功能，再把通过的规格写回05和06；未来 Sol 只执行通过门槛的施工包。

这不是承诺系统能给人生定向，而是把“记住、联想、判断、推进”逐项变成可检验的产品能力。
