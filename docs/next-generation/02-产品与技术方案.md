# 产品与技术方案

本文件定义R2的Alpha基础契约（T00–T11）及通用底层规则。正式版扩展由05定义，任务顺序以06为准；主题、Dream增强、成果、文档解析和编辑管理已纳入本次Windows正式版。参数是本项目初始默认值，不是第三方服务限制或已实测性能。

## 1. 架构选择

保留 Electron 主进程、preload 桥接、React 界面和共享 TypeScript 类型四层。首批不换框架、不引入服务端、不迁移为 SQLite 主库、不加入大型 Agent 框架。

新能力按数据流组织：

```text
文字 / 图片 / 公开链接 / 手动正文
                 ↓ 先本地保存
        Note + Source + 原始附件
                 ↓ 可恢复任务
      正文提取 / OCR / 按需图片理解
                 ↓
     本地关键词检索（可选轻量索引） ← 笔记 / Wiki / 封存 Wiki
          ↓                     ↓
       普通搜索            片段召回 → DeepSeek → 引用答案

个人笔记 → 分类 → 按 Wiki 分组的合并任务 → Wiki
个人笔记 / 显式选定外部资料 → Dream / 主题复盘
```

职责规定：React 负责展示与用户操作；文件访问、API Key、第三方 HTTP、索引和任务执行留在主进程。新业务服务通过存储/模型接口工作，不能直接操作 BrowserWindow；由 IPC 适配层推送进度。已有代码按任务逐步接入，不先进行全仓重构。

Windows 首版只有一台指定主设备写正式知识库、运行自动 AI。坚果云是文件运输层，不是分布式锁。第二台电脑并发整理同一库不在支持范围内；移动端只写采集包。

## 2. 界面与用户流程

### 2.1 采集

- 在现有 Notes 输入区增加“存链接”和“图片”入口；保留文字输入、附件、Alt+Enter 和保存按钮。
- 粘贴图片或选择图片后，显示缩略图、识别开关与个人批注。新采集图片默认执行 OCR；既有附件不会在升级时自动全量上传。
- 存链接表单包含 URL、个人批注，保存后立即生成卡片。正文提取失败时仍保留 URL，提供“粘贴正文”“重试”“打开原网页”。
- 详情分为“我的记录”“原始资料”“AI 整理”。OCR/网页正文不能覆盖用户的 `raw_content`。
- 图片详情支持原图与识别文字并排查看；可手工修正识别文本，保留原始提取版本。修正后只更新索引，默认不重复 OCR。
- 图片理解单独按钮触发，用于图表、画面和非纯文字含义；结果标注为 AI 理解，与 OCR 文字分开。
- 卡片状态使用“已保存 / 待提取 / 提取中 / 可检索 / 失败 / 结果待确认”。保存成功与处理成功分别表达。

### 2.2 搜索与问答

- 保留 Notes 的当前列表搜索；新增全局“搜索与问答”页面，共用同一关键词检索服务，避免再建一套数据副本。
- 全局范围可选笔记、资料、Wiki；默认全部，封存 Wiki 默认包括，Dream/生成答案默认不包括。
- Wiki 页保留“当前 Wiki”查找入口，另提供“所有 Wiki”；跨文档命中跳转全文并定位相关段落。
- 普通搜索不调用模型。结果显示标题、命中片段、来源类型、日期和打开来源入口。
- “问我的笔记”是显式按钮，不因用户每输入一个字就调用 API。Alpha单轮问答，支持查看、保存答案；正式版按05第4节增加有限轮会话与追问，不引入无限长期对话记忆。
- 回答下展示实际使用的来源；引用编号可点击。没有足够证据时明确表示未找到，不把模型常识伪装成个人笔记事实。
- 来源变更时，已保存答案标注“来源已变化”；来源删除时显示失效提示，不跳到无关段落。

### 2.3 外部资料进入 Wiki 的规则

普通个人笔记延续现有自动分类与 Wiki。图片、网页等外部资料默认进入资料检索，可自动生成短标题/摘要/标签，但默认不参与 Wiki/Dream。用户在详情页点击“纳入 Wiki/Dream”后参与后续整理。这防止把收藏文章的观点自动当成用户自己的观点。

已生成 Wiki 不是源笔记删除后的自动同步副本。删除或更改已引用资料时标记相关 Wiki“来源有变更”，保留历史快照，并提供手动重建；不得静默删改历史总结。

## 3. 数据与最小接口契约

### 3.1 文件布局

```text
sync_dir/
  notes/                  继续保存原 Note JSON
  files/                  原附件；新增附件采用 UUID 存储名
  sources/                新增来源元数据及提取文本
  answers/                Alpha用户显式保存的问答结果；正式会话另用conversations
  collections/            正式版主题知识库（见05）
  wikis/                  保留当前、sealed、backups、.prev
  provenance/             新 Wiki/Dream 的来源清单与输入指纹
  captures/               T23/T24可选手机不可变采集包
  receipts/               导入回执
  inbox.txt               保留旧中转入口

app.getPath('userData')/libraries/<库路径哈希>/
  jobs/                   本机任务状态与第三方 jobId
  search/                 可选的可重建本地索引
  usage/                  调用次数、token/页数，不记正文或密钥
```

同步内容以原始资料、可移植文本和用户保留的产物为主。可选的本地索引、运行锁和临时队列不进入坚果云。换机可从正式数据重建索引，但不能自动重跑整库付费任务。

### 3.2 类型约定

在 `src/shared/types.ts` 扩展已有类型，新增字段默认可选，以读取旧文件。新记录写 `schema_version: 2`；不批量重命名旧笔记。

| 类型 | 最小字段 | 约定 |
|---|---|---|
| Note 扩展 | `schema_version`, `created_at_ms`, `updated_at_ms`, `source_ids`, `origin`, `include_in_wiki`, `capture_id` | origin为personal/imported/derived；旧笔记视为personal并默认纳入Wiki；新导入和派生产物默认不纳入 |
| SourceRecord | `id`, `note_id`, `kind`, `title`, `url?`, `captured_at_ms`, `asset_names`, `content_hash`, `extracted_text`, `edited_text?`, `segments`, `status`, `provider?`, `model?`, `extracted_at_ms?`, `error?` | kind为image/web/text，正式版T15增加pdf/docx；content_hash 是有效文本指纹，手工修正后改变；原始提取文本保留 |
| SourceSegment | `id`, `start`, `end`, `page?` | start/end 是对应有效文本的 UTF-16 索引；文本变化重新分段；页码从1开始 |
| SourceRef | `kind`, `id`, `content_hash`, `segment_id?`, `quote`, `page?` | kind 为 note/source/wiki；用于搜索、回答和正式版Dream引用；不接受模型生成任意路径 |
| Job | `id`, `library_id`, `kind`, `target_id`, `input_hash`, `state`, `attempts`, `provider_job_id?`, `next_run_at?`, `last_error?`, `created_at_ms`, `updated_at_ms` | 队列状态见下一节；provider job ID 一律字符串；任务绑定启动时的库 |
| SearchRequest | `query`, `kinds`, `date_from?`, `date_to?`, `category?`, `collection_id?`, `offset`, `limit` | 默认20条，上限100；日期范围由统一时间工具解析 |
| SearchHit | `ref`, `title`, `snippet`, `score`, `note_id?` | score 仅作本地排序，不是事实置信度 |
| AnswerRecord | `id`, `question`, `answer_markdown`, `citations`, `created_at_ms`, `model`, `usage?` | citations 为 SourceRef 列表；先验证引用再允许保存 |

新增服务接口：`capture.create(input)` 返回已落盘 noteId；`sources.extract(sourceId)` 返回 jobId；`jobs.list/retry/cancel` 管理任务；`search.query(request)` 返回命中与总数；`knowledge.ask({question, filters})` 返回 jobId；`sources.resolve(ref)` 返回来源及是否过期。进度事件统一为 `{jobId,state,progress?,error?}`，不发送凭据或整库内容。

`input` 为 text/image/url 的判别联合类型；renderer 传文本或经文件选择/粘贴授权的临时句柄，不能直接传任意可读绝对路径。链接只接受 http/https。跨 IPC 校验类型、长度、库内路径与记录是否存在。

旧 `window.api.notes.*` 保持可用；新增命名空间逐步接入。主进程返回明确成功/失败，不能继续“写失败只打日志，却向 UI 报成功”。

### 3.3 保存、版本和兼容

- Note ID 继续使用数字毫秒风格；单主设备使用单调递增分配器，候选值取当前毫秒与上次值+1的较大者，并用排他创建处理落盘冲突。不能仅加 sleep 防碰撞。
- UUID 用于 Source、Job、Answer、Capture 和新附件；不把 Note ID 全部改为 UUID，因为旧加载正则和 Dream 的 `parseInt(id)` 都依赖数字。
- 新增时间字段读取优先级：有效 `created_at_ms` → 合法数字 ID → 合法 `created_at`。显示与时间筛选统一走工具函数，不再在各服务临时推断时间。
- 更新采用同目录临时文件写完后替换；失败保留旧文件并明确报告。启动清理仅针对可确认废弃的临时文件；同步观察到的半文件只等待重读，不删除。
- 主进程集中串行提交同一 Note 的写入。AI 保存前重新读取最新记录、比较输入指纹，只补丁更新其拥有的 AI 字段；用户正文、附件和来源不得被旧对象整条覆盖。
- 指纹采用 SHA-256；文本以规范化换行后的实际输入计算，图片以原始字节计算。缓存键还包含供应商、模型、处理选项和提示词版本。
- 历史文件无来源信息时显示“历史内容，未记录出处”，不补造来源。旧文件按需读取升级，不在首次启动触发全库 AI。

## 4. 可恢复任务与导入

切换 sync_dir 时停止旧库派发，取消本机等待并使旧界面请求失效；已知远端任务保留在旧库对应本机状态中。任务固定绑定库ID与解析后的路径，异步完成时不能重新读取全局配置并写进新库。

图片原始字节指纹用于提取任务的 input_hash；SourceRecord.content_hash 用于有效文本与引用版本，二者不能混用。用户修正文字后索引/引用失效，但原图OCR缓存仍可保留。

### 4.1 任务状态

状态固定为 `queued/running/waiting_external/retry_wait/succeeded/failed/needs_attention/cancelled`。业务界面的文字状态从此映射，不再靠 Note.ai_status 同时表达 OCR、分类和 Wiki 三件事。

- 重启恢复 running：有远端 jobId 则继续查询；无远端任务且可确定未提交则回 queued；无法判定是否已被第三方接受则 needs_attention，不能无限自动重复提交。
- 用户取消只保证停止本机等待/后续操作；没有第三方取消接口时不承诺远端停止或退费。
- 自动网络尝试每任务最多3次，累计 attempts 跨重启保留；若所属产品动作另有更严格调用上限，按较小值执行，并共享actionId预算（见05第9节）。401/403、无效参数、额度耗尽不盲目重试；429 尊重 Retry-After；网络/5xx 退避2秒、8秒，后续人工重试。
- 第三方正常轮询不计为失败次数。提交、查询、结果下载分开记录，不把“下载结果失败”误当成“重提任务”。
- 默认 DeepSeek 同时最多2个请求，PaddleOCR 同时最多1个未结束的远端任务；交互问答优先于未开始的后台整理。
- 不叠加现有 callLlm 的三次内部重试和任务队列的三次重试。接入后由队列统一负责重试，单次客户端调用只尝试一次。
- 每个任务以 kind+target+inputHash 去重；已有成功结果复用，已有运行任务返回同一个 jobId。

无法对无幂等键的第三方 API 保证严格“只计费一次”。目标是缓存命中不调用、已有 jobId 不重提、响应丢失时停止自动重提，并向用户说明状态。

### 4.2 旧 inbox 恢复

当前源码在 `finally` 删除 processing 文件，且批量保存仍使用 Date.now；两者是新功能前置验证项。

新处理顺序：将 inbox 接收为带唯一批次 ID 的处理中快照 → 为每个 block 分配固定导入标识 `batchId:blockIndex` → 保存 Note（带 capture_id）→ 记录进度 → 全部成功才归档快照。中途失败保留快照，重启以 capture_id 扫描去重后继续。不能只靠内存计数判断处理到哪一条。

保留 BOM、LF、CRLF、CR 和空白分隔行兼容。重复出现的两个相同文本块应成为两条笔记，不能仅按文本 hash 去重。新建空 inbox 失败时也必须保留已接收内容。

历史 `processing.txt` 启动时优先转换为可恢复批次；处理期间新到的 inbox 留待下一批。坚果云冲突副本列为待检查条目，不把未知副本自动当作新笔记或静默忽略。

## 5. 图片、网页与文档

### 5.1 PaddleOCR 接入：按用户提供的真实示例

参考工程根目录 `paddleAPI.txt` 的接口结构，不复制其 token，也不直接执行示例脚本。生产实现使用 TypeScript/主进程 HTTP，不新增 Python 运行时。

- 提交：`POST https://paddleocr.aistudio-app.com/api/v2/ocr/jobs`；默认模型 `PaddleOCR-VL-1.6`，配置中允许修改。
- 本地图片使用 multipart：`file`、`model`、JSON 字符串 `optionalPayload`。让 HTTP 实现自动生成 multipart boundary。
- 默认关闭方向分类、去弯曲、图表识别，沿用提供的示例；详情中的高级选项允许针对旋转页面或图表重新处理，选项变更形成新缓存键。
- 记录 `data.jobId` 后轮询 `GET .../jobs/{jobId}`；识别 pending/running/done/failed，进度来自 extractProgress。
- 每5秒查询一次，持续等待10分钟后暂停本机轮询并显示“仍在处理，可继续查询”；保留 jobId，不认定远端失败，不重复上传。
- 完成后下载 `data.resultUrl.jsonUrl` 的 JSONL；逐行读取 `result.layoutParsingResults`，提取 `markdown.text`，保存页序和本地可检索文本。
- 远端返回的 Markdown 图片不是永久存储。正文引用到的图片下载到受控 assets 目录并改写引用；首版不保存 outputImages 中的调试可视化。下载链接不转发 API Authorization，远端提供的路径不能直接作为本地写入路径。
- 部分页面失败必须展示页数与失败范围，不能把缺页结果标为完整成功；结果 URL 失效先重新查询原 jobId。
- 首版图片限制：PNG/JPEG/WebP，单张不超过20 MiB，单次最多10张；这是本应用保护阈值。长图提示检查识别质量，不静默压缩到文字不可读。
- 新凭据通过设置录入并存于本机凭据存储；不写 sync_dir、不提交 Git、不放 renderer。供应商额度以实际账户及返回值为准，不把“每日免费额度很多”写成永久固定数。

官方也提供云端异步 API 的 TypeScript 客户端，说明该路线无需本地部署 OCR 模型。本项目默认先做小型 HTTP 适配器，以对齐用户样例并减少 SDK 升级牵连。[PaddleOCR 官方说明](https://www.paddleocr.ai/main/en/version3.x/inference_deployment/serving/paddleocr_official_api/overview.html)

### 5.2 DeepSeek 图片理解

独立于 OCR，默认手动触发。当前官方文档提供 `deepseek-flash` 图片输入，Chat Completions 的用户消息采用 text/image_url 内容块；不得仅换模型名却继续把图片路径当文字发送。[官方视觉接口](https://api-docs.deepseek.com/guides/vision/)

保留工程已有 `/v1/chat/completions` 端点；增加单独可配置的视觉模型字段，首次集成用测试图片验证。默认每次1张、输出不超过1200 tokens；概览选择 low，读取细小文字/图表时可选择原始精度。OCR 额度用尽不能自动改走付费视觉模型，需用户显式点击“改用图片理解”。

### 5.3 公开网页收藏

R3注记：本节仅规定安全抓取与快照，不代表网页“解读”已经设计完成。面向目标的速读、对照、失败诊断及效用验证见08；未通过门槛时仅交付可靠收藏和手动正文。

使用主进程 HTTP 获取 HTML，再通过 Mozilla Readability 提取主文，保存标题、原始 URL、最终 URL、采集时间、纯文本/安全 Markdown 和内容指纹。Readability 解决正文提取，不解决登录、反爬或所有动态网站。[项目说明](https://github.com/mozilla/readability)

- 超时20秒、最多5次重定向、HTML 正文上限5 MiB；每次跳转重新检查目标。仅允许公开 http/https，拒绝 file、内网/本机地址和不支持类型。
- 默认不加载页面脚本，不运行远端 HTML，不拷贝用户浏览器 Cookie。阅读内容用现有安全 Markdown 渲染；禁用任意原始 HTML 和可执行链接。
- 页面取不到正文时，明确返回原因并切换手动正文入口；网页快照的正文与用户批注分开。
- URL 去掉 fragment、规范化主机大小写，但不擅自删除 query 参数。相同 URL 命中已有记录时默认打开已有项，可选择创建新快照；不同时间快照不自动覆盖。
- 微信公众号、知乎、小红书等仅在公开内容可提取时成功；登录帖子和评论区通过用户粘贴或图片留存，首版不做平台专用爬虫。
- 外部正文作为资料输入模型，不作为 system 指令；其中“忽略此前规则”等文本不得改变任务或触发工具执行。

### 5.4 文档扩展（正式版T15）

TXT/Markdown 直接读文本；PDF 先用 PDF.js 提取文字与页码，扫描页显式选择 OCR；DOCX 用 Mammoth 的纯文本接口。PPT、旧 DOC、加密 PDF 首轮不支持，提示转换。解析失败仍保存原附件。

选择理由是复用 JS 工程、避免常驻解析服务器；不能把可解析所有复杂表格/版式作为承诺。先做20 MiB/100页保护阈值，超出时让用户选范围，不静默截断。[PDF.js](https://mozilla.github.io/pdf.js/) · [Mammoth](https://github.com/mwilliamson/mammoth.js)

## 6. 本地检索与带引用问答

### 6.1 索引

首版只做本地关键词/字段全文检索，先扩展现有搜索并用1千/1万条合成资料测量查询与内存。若未达目标，再评估零外部依赖的轻量 MiniSearch 作为倒排索引；它是普通全文检索库，不做语义匹配，也不是必须引入的包。[MiniSearch官方项目](https://github.com/lucaong/minisearch)。不安装 embedding 模型、向量数据库、ANN索引或仅为语义检索服务的运行时。

- 索引：个人正文、资料有效文本、标题、标签、当前/封存 Wiki。AI 评论、历史答案、备份副本默认排除，防止派生内容循环引用。
- 中文可用运行时自带 Intl.Segmenter，必要时补充连续汉字双字词；单字查询保留单字路径，英文按词并小写化。若采用索引，入库/查询共用分词工具；不下载单独分词模型。
- 按段落切分，目标每块约800字符，上限1200字符，长段相邻重叠约100字符。每块携带稳定来源 ID、文本指纹与段落位置。
- 标题权重3、标签2、正文1；相同来源去重展示，展开可看更多命中。
- 若启用索引，应用写入后增量更新；启动核对索引版本与文件指纹；目录事件加去抖并定期核对清单，处理坚果云外部变更。暂时读失败保留旧索引并标记待复核，不能据一次读取失败批量删除。若扩展现有逐文件搜索，保持同等失败可见和结果一致性。
- 删除来源立即移除活跃索引；已有答案保留引用状态但不把删除内容重新放回可搜索集合。

本轮明确排除语义检索。关键词没有覆盖的同义表达可能漏召回，界面应显示查询词、范围与无结果状态，允许用户改词或选定资料；同义问法评测用于记录已知限制，不触发 embedding 或更重依赖的补救提案。

### 6.2 问答步骤

1. 解析用户显式范围，在本地召回前30个片段；按来源去重、相邻片段合并。
2. 无命中时明确显示“当前关键词与范围下没有证据”，让用户改词、放宽范围或手动选定资料；不自动调用模型改写查询或用语义检索补全。
3. 最多选8个片段、合计不超过8000字符进入回答；单一来源通常不超过3片段。UI 显示范围和使用来源数，不宣称已经完整阅读整库。
4. 构造临时来源编号 S1…Sn；system 中定义回答与引用规则，资料置于 user 内容的明确边界内。
5. DeepSeek 返回 JSON：`answer_markdown` 与 `citations[{source_id,quote}]`。主程序验证 source_id 在本次候选内、quote 是对应片段的原文子串，随后映射到 SourceRef。
6. 无效引用最多做一次格式修复；仍不合法则显示“未生成可核对的回答”，保留搜索结果，不发布带假出处的答案。修复与网络重试共享单动作预算，整个问答最多2次实际模型HTTP请求，含网络重试且所有子步骤共享，详见05第9节。
7. 结果默认临时展示；用户点击保存才写 answers。缓存键含问题、过滤条件、来源集合版本（若启用索引也含索引代次）、模型、提示词版本；任一变化则失效。

引用存在只证明出处可定位，不自动证明推理正确。答案应区分“资料明确记载”和“基于资料的推测”；验收包括人工检查事实是否由引用支持。

首版不默认联网搜索，不用外部网络知识填补个人知识库空缺，不在用户输入问题时自动分析其人格或长期偏好。

## 7. Wiki、Dream 与调用成本

### 7.1 Wiki 合并

新任务入队时按笔记 created_at_ms 的本机日历月份固定 month；旧笔记使用统一时间回退规则。积压任务跨月执行不改投到处理月份；已有历史Wiki不因此重写或迁移。

- 保留自动更新与分类/月度文件习惯；同一 category+month 串行，最多2个不同 Wiki 并行，受全局 DeepSeek 并发上限约束。
- 每个 Wiki 收集“首条到达后30秒”内已完成分类的笔记，或者累计5条立即执行，先满足者触发；按创建时间、ID 排序。必须用首条时间，不能无限滑动防抖饿死队列。
- 一批合并只发送一次旧 Wiki 与本批新材料。单批新增内容上限12000字符，超出拆批，不截掉用户内容。
- 旧 Wiki 加本批材料超过24000字符时暂停该 Wiki 自动合并并提示封存；保留待处理任务，用户封存后继续。首版不静默拆章或自动封存。
- Wiki 输出保留来源标记，另存 provenance 输入清单。提交前持久化包含旧文件指纹、新产物指纹、来源清单和候选内容路径的提交日志，再替换正式Wiki、写来源清单，最后消费队列。崩溃恢复时若正式文件已等于新指纹，则只补齐清单/任务状态；仍等于旧指纹才重试提交；两者都不是则保留候选待审，不重新调用模型或覆盖用户修改。
- 生成期间用户封存/修改 Wiki：提交前核对旧 Wiki 指纹。发生变化则保留候选结果为待审，不覆盖新状态。
- 保留当前备份、diff 与长度保护，但“出现标题/标签”不能视为完整性证明。源笔记始终保留；新格式失败可回看候选与旧版。

### 7.2 Dream（T10正确性，T19完整增强）

T10分离释放运行锁与更新成功状态：失败、取消、空结果不登记成功；成功保存本次实际使用笔记ID/输入指纹。晚完成分类的旧笔记不能被时间戳游标跳过。首次升级把已有完成笔记记为baseline，不全库付费重跑。周分组采用真实周起始日期。

T19的片段覆盖、partial/full/attempted-version、材料预算及结构化洞察以05第6节为准。Alpha的按笔记覆盖只是基础实现，正式版不能将节选当作全文已覆盖。反思/关联/点评的输入边界以05第5节为准，生成结果默认不回流为原始证据。

### 7.3 成本默认值

| 操作 | 初始策略 |
|---|---|
| 普通保存/搜索 | 0 次模型调用 |
| 图片 OCR | 同 hash+模型+选项成功后复用；重启继续原 jobId |
| 新资料短摘要 | 只处理有效文本前6000字符并明确“摘要基于节选”；完整文本仍可搜索 |
| 分类 | 延续自动处理；标题/摘要/分类/标签一次返回 |
| 问答 | 通常1次，含格式修复或网络重试最多2次；回答输出上限1600 tokens |
| Wiki | 同类别小批量合并；不每条都立即重写整篇 |
| 图片理解/反思/关联 | 用户手动触发；相同输入复用结果 |
| 历史库 | 不自动全量 OCR、重分类、重建 AI 摘要 |

新增客户端返回 `{text, model, usage?, finishReason?}`，保留旧 callLlm 的兼容包装。记录供应商返回的实际 token/页数；没有 usage 时显示“未知”，不编造费用。配置允许填写每百万 token 价格用于估算，不把当前价格永久写死。

分类输出上限800 tokens；Wiki 上限8000 tokens。若 finishReason 表示截断，结果不能覆盖正式 Wiki；提示缩小批次或封存。统一提供取消、当日调用数量和失败次数，不在日志写请求全文。

## 8. 正式版主题知识库、会话与成果

完整规格见[05-完整产品规格.md](05-完整产品规格.md)。Collection成员只保存Note ID，自动包含其有效Source，不复制正文、不改变category。正式版增加conversations、insights、artifacts目录与本机drafts，均沿用本文件的库隔离、原子保存和任务恢复原则。

原answers文件保留可读；正式版“已保存答案”入口能够列出这些单轮历史，不自动迁移为伪造的多轮会话。成果版本、会话状态、手工编辑和来源失效由05确定。

## 9. 已知限制与回滚

首版不解决多台电脑同时编辑同一库，不保证任何社交平台都可解析，不承诺无 OCR 误识别或无模型推理错误。用原始资料保留、引用核对、重试与失败可见来保证可检查性。

功能逐项由本机 feature flag 开启。先在数据副本上验收，记录备份路径和源基线；正式启用前备份完整 sync_dir 与本机配置。回滚先停任务再恢复备份，不能让 v2.9.0 和新版本轮流写同一新版库。
